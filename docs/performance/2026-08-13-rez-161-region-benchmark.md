# REZ-161 리전 배치 성능 측정

## 목적

Supabase가 서울에 고정된 현재 구조에서 프론트엔드와 백엔드의 배치 조건을 비교하고, `grabbin.me/founder` 주요 경로의 응답 시간·브라우저 완료 시간·Worker CPU를 기준으로 운영 설정을 정한다.

## 측정 조건

- 측정 시각: 2026-08-13 (Asia/Seoul)
- 대상: `https://grabbin.me/founder`, `https://api.grabbin.me/pages/founder`
- 요청 위치: 측정 실행 환경의 Cloudflare `AMS`, `cf-ipcountry=NL`
- 주의: 한 위치에서 측정했으므로 전 세계 사용자의 실제 수치를 대표하지 않는다.
- 각 조건: HTML 3회, 공개 페이지 API 3회, 무쿠키 세션 조회 3회, 로그인 브라우저 새로고침 3회
- HTML 크기: 131,384 bytes
- 공개 페이지 API 크기: 28,357 bytes
- 판정: HTTP 200, 브라우저 주요 내용 표시, `outcome=ok`, CPU 기록

API TTFB는 Seoul 고정에서 무설정보다 약 29%, Smart보다 약 29% 낮았다. Supabase와 백엔드 실행 위치를 가깝게 만든 효과로 판단한다.

## 브라우저 측정

`/founder` 로그인 상태에서 실제 새로고침 후 DOM이 준비되고 `Follow`, 사용자 이메일, `Send` 내용이 표시되는지 확인했다.

| 조건 | 1회 | 2회 | 3회 | 평균 | 결과 |
| --- | ---: | ---: | ---: | ---: | --- |
| 무설정 | 1,324ms | 1,257ms | 1,213ms | 1,265ms | Pass |
| Smart | 1,894ms | 1,206ms | 1,172ms | 1,424ms | Pass |
| Seoul 고정 | 1,627ms | 1,854ms | 1,283ms | 1,588ms | Pass |

브라우저 완료 시간은 캐시·클라이언트 상태·측정 위치의 흔들림이 커서 Seoul 고정이 모든 실행에서 가장 빠르다고 단정할 수 없다. 다만 API TTFB는 Seoul 고정이 일관되게 가장 좋았다.

## Worker CPU 측정

CPU는 네트워크 대기 시간이 아니라 Worker JavaScript 실행 시간이다.

| 조건 | 관측값 | 해석 |
| --- | --- | --- |
| 무설정 | 무쿠키 세션 0~6ms, 공개 캐시 적중 약 1~10ms, DB·인증 미적중 경로 15~46ms | 캐시 경로는 목표에 가깝지만 콜드 경로는 초과 |
| Smart | 무쿠키 세션 0~9ms, 공개 캐시 적중 1~2ms, 공개 콜드 경로 25~30ms | Smart가 CPU 자체를 줄이지는 않음 |
| Seoul 고정 | 무쿠키 세션 0~10ms, 공개 캐시 적중 1~4ms, 공개 콜드 API 12ms, 로그인 브라우저 경로 27~31ms 관측 | DB·인증 콜드 경로는 여전히 10ms 초과 |

모든 관측 요청은 `outcome=ok`였지만, 10ms 초과가 반복되어도 안전하다는 뜻은 아니다. 이번 코드 개선으로 무쿠키 세션 조회를 빠르게 종료하고 공개 페이지 결과를 30초 캐시하도록 만들었으나, DB 조회와 Better Auth 세션 확인이 필요한 첫 요청까지 항상 10ms 이하로 만드는 것은 달성하지 못했다.

## 설정 결정

최종 설정은 두 Worker 모두 Seoul 고정이다.

```jsonc
"placement": {
  "mode": "targeted",
  "region": "aws:ap-northeast-2"
}
```

이유는 백엔드와 Supabase 리전이 서울로 고정되어 있고, API TTFB가 가장 낮았기 때문이다. 정적 파일은 계속 Cloudflare 엣지에서 제공되며, 동적 HTML·API만 데이터베이스에 가까운 위치에서 실행된다. Smart Placement는 여러 위치의 충분한 트래픽을 보고 최대 15분 동안 배치 위치를 학습하므로, 이번 짧은 측정만으로 안정적인 Smart 결과라고 판정하지 않았다.

## 시나리오 기록

### REZ-161-01 주요 공개 경로

- 결과: **Pass**
- Given: 각 배포 조건에서 공개 페이지가 존재한다.
- When: `/founder`와 `/pages/founder`를 각각 3회 조회한다.
- Then: 모두 HTTP 200이고 공개 콘텐츠가 표시된다.
- Evidence: 위 응답 표, API 28,357 bytes, 모든 API 요청 `outcome=ok`.

### REZ-161-02 로그인 브라우저 경로

- 결과: **Pass**
- Given: 인앱 브라우저에 로그인되어 있다.
- When: `grabbin.me/founder`를 3회 새로고침한다.
- Then: DOM이 준비되고 사용자 페이지 내용이 표시된다.
- Evidence: 위 브라우저 표, 3개 조건 모두 오류 없이 `Follow`, 이메일, `Send` 표시.

### REZ-161-03 쓰기·삭제 경로

- 결과: **Not Run**
- Given: 실제 페이지·아이템을 바꾸거나 삭제할 수 있는 로그인 계정이 있다.
- When: 각 조건에서 실제 POST/PATCH/DELETE를 실행한다.
- Then: 데이터 변경 결과와 CPU를 비교한다.
- Evidence: 사용자 데이터 변경을 피하기 위해 실제 쓰기·삭제 요청은 실행하지 않았다. 따라서 이 문서는 읽기·렌더링 기준으로 설정을 결정하며, 쓰기·삭제의 전 세계 실측값은 아직 없다.

## 결론

Seoul 고정 배포를 적용했고, 공개 API 응답은 세 조건 중 가장 빠른 결과를 보였다. 다만 Free 요금제의 10ms CPU 목표를 모든 콜드 DB·인증 요청에서 보장하지 못했으므로, 해당 목표를 엄격히 요구한다면 다음 단계는 공개 데이터 사전 계산 또는 엣지 캐시/KV 기반 읽기 모델이다. 실제 쓰기·삭제는 안전한 전용 테스트 데이터가 준비된 뒤 별도 측정해야 한다.
